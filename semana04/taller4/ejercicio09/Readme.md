Objetivo: Diseñar un sistema de seguridad en dos fases: primero, identificar al usuario seleccionando dinámicamente entre múltiples proveedores de autenticación; segundo, procesar una secuencia de validaciones de acceso.  

1. Rol de cada patrónStrategy (Autenticación): Resuelve el "cómo" inicio sesión (la llave). Encapsula las distintas APIs o lógicas (Google, Biometría, Password) en clases independientes. Evita que el AuthService tenga sentencias if (tipo == "GOOGLE") acopladas a librerías externas.  Chain of Responsibility (Autorización): Resuelve el "control de seguridad" post-autenticación. Permite encadenar reglas de negocio (permisos, ubicación, horario) donde cada validador decide independientemente si el flujo continúa o si se lanza una excepción de acceso denegado.  

2. Cómo interactúan (Multivariable)El cliente solicita acceso y el sistema determina qué Strategy de autenticación le corresponde a su perfil.  La Strategy se ejecuta (authenticate()). Si falla, el proceso muere ahí. Si es exitosa, retorna un contexto de identidad.Inmediatamente, el sistema inyecta ese contexto en el primer eslabón de la Chain of Responsibility.  El contexto viaja a través de los validadores (CredentialValidator -> PermissionValidator -> LocationValidator). Si la cadena se completa sin interrupciones, el acceso es finalmente concedido.  

3. Justificación Arquitectónica (Clean Code, SOLID y XP)Single Responsibility Principle (SRP): La estrategia biométrica no necesita saber sobre los horarios laborales de la empresa. El validador de ubicación no necesita saber si entraste con Google o Microsoft. Cada clase hace una sola cosa.

Open/Closed Principle (OCP): En un entorno Ágil, si el próximo mes el equipo de ciberseguridad exige validar la dirección IP (VPN), solo creamos un IpValidator y lo añadimos a la cadena. No modificamos la lógica existente.Fail-Fast & Test-Driven Development (TDD): La cadena implementa un patrón de "falla rápido". Tan pronto como una validación falla, se lanza una excepción. Esto hace que escribir pruebas unitarias sea trivial: inyectamos un usuario Mock, configuramos la cadena hasta el eslabón deseado y verificamos que lance la excepción correcta.
